# Kubernetes Logs & Events

This section covers two important Kubernetes troubleshooting tools:

1. **Logs** — Used to understand what an application is doing inside a container.
2. **Events** — Used to understand what Kubernetes is doing with your resources.

Understanding the difference between Logs and Events is essential when debugging Kubernetes applications.

---

# 1. Logs — Application Output

## What are Kubernetes Logs?

Kubernetes logs are the **standard output (`stdout`) and standard error (`stderr`) streams** produced by processes running inside containers.

The application itself generates the logs.

Examples of applications that generate logs:

- Node.js
- Python
- Java
- Nginx
- Go
- PHP
- Any other containerized application

For example, an application might produce:

```text
Application started
Connecting to database...
Database connection successful
Application is running
Application is healthy

Kubernetes makes this output available through the kubectl logs command.

Why are Logs Useful?

Logs are primarily used for application-level debugging.

They can help answer questions such as:

Did my application start successfully?
Did the application connect to the database?
Why did an API request fail?
Did the application throw an exception?
What happened immediately before the application crashed?
Is the application receiving requests?

For example:

Application started
Connecting to database...
Database connection failed

From this log we can immediately suspect a database connection problem.

Basic Log Commands
View logs for a Pod
kubectl logs <pod-name>

Example:

kubectl logs logs-demo

This displays the logs produced by the container inside the Pod.

Stream logs in real time
kubectl logs -f <pod-name>

The -f flag means follow.

Example:

kubectl logs -f logs-demo

This keeps the command running and displays new log messages as they are produced.

Example:

Application is healthy
Application is healthy
Application is healthy
Application is healthy

Press:

Ctrl + C

to stop following the logs.

Ctrl + C stops the log stream. It does not stop or delete the Pod.

View logs from a specific container

A Pod can contain multiple containers.

In that case, specify the container using:

kubectl logs <pod-name> -c <container-name>

Example:

kubectl logs my-pod -c app

This is useful when a Pod contains multiple containers such as:

Pod
├── application
└── sidecar
View logs from a previously crashed container

This is one of the most useful commands when troubleshooting crashes.

kubectl logs <pod-name> --previous

Example:

kubectl logs crash-demo --previous
Why use --previous?

When a container crashes, Kubernetes may restart it.

The current container may already be running again, meaning:

kubectl logs crash-demo

may show logs from the new container instance.

To see what happened immediately before the previous container crashed:

kubectl logs crash-demo --previous

This is particularly useful for diagnosing:

Application crashes
Exceptions
Database connection failures
Configuration errors
Invalid environment variables
Startup failures
2. Events — Cluster Activity
What are Kubernetes Events?

Kubernetes Events are objects generated by Kubernetes components to describe important activity happening inside the cluster.

Events are generated by components such as:

Kubelet
Scheduler
Controllers
Other Kubernetes components

Unlike application logs, Events describe what Kubernetes is doing with your resources.

Why are Events Useful?

Events are mainly used for cluster-level and infrastructure troubleshooting.

They can help identify problems such as:

Pod scheduling failures
Image pull failures
ErrImagePull
ImagePullBackOff
CrashLoopBackOff
Readiness or liveness probe failures
Container creation failures
Node problems
Resource constraints

For example:

FailedScheduling
0/1 nodes are available

This indicates that Kubernetes could not find a suitable node to schedule the Pod.

Another example:

Failed to pull image

This indicates that Kubernetes could not download the container image.

Basic Event Commands
View events in the current namespace
kubectl get events

This displays Events associated with resources in the current namespace.

Sort events by time

A very useful troubleshooting command is:

kubectl get events --sort-by='.lastTimestamp'

This makes it easier to understand what happened chronologically.

Example:

Scheduled
Pulling
Pulled
Created
Started

This can help reconstruct the lifecycle of a Pod.

Watch events in real time
kubectl get events -w

The -w flag means watch.

New Events will appear as they are generated.

Press:

Ctrl + C

to stop watching.

Events for a Specific Resource

The most common way to investigate Events for a particular resource is:

kubectl describe <resource> <name>

For a Pod:

kubectl describe pod <pod-name>

Example:

kubectl describe pod crash-demo

The Events section appears near the bottom of the output:

Events:
  Type     Reason     Message
  ----     ------     -------
  Normal   Scheduled  Successfully assigned ...
  Normal   Pulled     Container image pulled
  Normal   Created    Created container
  Normal   Started    Started container

For a failing Pod, you may see:

Warning  Failed
Warning  BackOff

These messages are extremely useful for troubleshooting.

Logs vs Events

Understanding the difference between Logs and Events is very important.

Feature	Logs	Events
Generated by	Application/container	Kubernetes components
Main purpose	Application debugging	Cluster/resource debugging
Shows	Application output	Kubernetes activity
Examples	Exceptions, API requests, DB errors	Scheduling, image pulls, container creation
Command	kubectl logs	kubectl get events
Resource-specific debugging	kubectl logs <pod>	kubectl describe pod <pod>
Useful for crashes	Yes	Yes
Useful for scheduling issues	Usually no	Yes
Useful for application errors	Yes	Usually no
Example Troubleshooting Workflow

Suppose a Pod is showing:

CrashLoopBackOff

Start with:

kubectl get pods

Then check the application logs:

kubectl logs <pod-name>

If the container has restarted:

kubectl logs <pod-name> --previous

Then inspect the Pod:

kubectl describe pod <pod-name>

Finally, inspect recent Events:

kubectl get events --sort-by='.lastTimestamp'

The troubleshooting flow becomes:

                 Pod Problem
                      |
                      v
              kubectl get pods
                      |
                      v
             What is the status?
                      |
          +-----------+-----------+
          |                       |
          v                       v
    Application issue        Kubernetes issue
          |                       |
          v                       v
    kubectl logs          kubectl describe
          |                       |
          v                       v
  --previous if needed     Check Events
Example: Application Failure

Suppose:

kubectl get pods

returns:

NAME         READY   STATUS             RESTARTS
crash-demo   0/1     CrashLoopBackOff   5

First check the logs:

kubectl logs crash-demo

You might see:

Application starting...
Database connection failed

Then check the previous container:

kubectl logs crash-demo --previous

Finally:

kubectl describe pod crash-demo

This allows you to combine:

Application-level information from Logs
Kubernetes-level information from Events
Example: Image Pull Failure

Suppose:

kubectl get pods

shows:

NAME          READY   STATUS             RESTARTS
image-demo    0/1     ImagePullBackOff   0

Application logs may not be useful because the container never successfully started.

Instead, use:

kubectl describe pod image-demo

Look at the Events section:

Failed to pull image
ErrImagePull
ImagePullBackOff

This tells us that the problem is with the container image rather than the application itself.

Example: Pending Pod

Suppose:

kubectl get pods

shows:

NAME           READY   STATUS
pending-demo   0/1     Pending

Since the container may not have started yet, application logs are generally not useful.

Instead:

kubectl describe pod pending-demo

Look at Events:

FailedScheduling
0/1 nodes are available

This indicates a scheduling problem.

Important Concept

A useful Kubernetes troubleshooting rule is:

Logs tell you what your application is doing. Events tell you what Kubernetes is doing.

Use:

kubectl logs

when investigating application behavior.

Use:

kubectl describe
kubectl get events

when investigating Kubernetes behavior.

In real-world debugging, you will often use both.

Quick Reference
Logs
# View logs
kubectl logs <pod>

# Follow logs
kubectl logs -f <pod>

# View logs from a specific container
kubectl logs <pod> -c <container>

# View logs from the previous container instance
kubectl logs <pod> --previous
Events
# View events
kubectl get events

# Sort events by time
kubectl get events --sort-by='.lastTimestamp'

# Watch events
kubectl get events -w

# View events for a specific Pod
kubectl describe pod <pod>
Practical Commands

For the Kubernetes troubleshooting exercises:

# Check Pods
kubectl get pods

# Inspect a Pod
kubectl describe pod <pod>

# Check application logs
kubectl logs <pod>

# Follow application logs
kubectl logs -f <pod>

# Check previous container logs
kubectl logs <pod> --previous

# Check cluster Events
kubectl get events --sort-by='.lastTimestamp'

These commands form the foundation of Kubernetes troubleshooting.

Key Takeaways
Logs come from the application running inside the container.
Events come from Kubernetes components.
Use kubectl logs to investigate application behavior.
Use kubectl logs --previous when a container has restarted or crashed.
Use kubectl get events to inspect cluster activity.
Use kubectl describe pod to inspect a Pod and its Events.
ImagePullBackOff is usually investigated through Events.
Pending Pods are usually investigated through scheduling Events.
CrashLoopBackOff can require both application Logs and Kubernetes Events.
Logs and Events complement each other during troubleshooting.

Remember:

Logs → What is my application doing?

Events → What is Kubernetes doing?
